CODEX MASTER REFACTOR PLAN
Minecraft Live React Dashboard
Project: E:\tiktok-minecraft\Minecraft Live\React Dashboard

PURPOSE
Refactor and reorganize the entire project so the codebase is readable, maintainable, modular, and easier to edit. The current Mob Battle page is approximately 4,000 lines and must be split into small focused files. This is a REFACTOR first, not a feature rewrite.

CORE RULES
1. Preserve existing behavior and functionality unless a change is explicitly required to fix a confirmed bug.
2. Do not redesign the business logic while merely reorganizing files.
3. Do not silently remove features because they look old or unused. Audit imports/usages first.
4. Preserve existing API endpoint behavior and request/response contracts unless a confirmed compatibility issue requires a change.
5. Preserve existing WebSocket behavior, TikTok event handling, Minecraft/LCon communication, gift handling, and Mob Battle event routing.
6. Zombie Apocalypse is a separate system. Do NOT merge it into Mob Battle and do NOT refactor its internals as part of this job unless a tiny dependency/import change is strictly required for compatibility.
7. Before deleting any file, search the entire repository for imports, references, dynamic imports, and route/navigation references.
8. Prefer many small files with one clear responsibility over giant files.
9. Avoid creating unnecessary abstraction layers. A module should exist because it has a clear responsibility.
10. Keep names descriptive and consistent with the existing project terminology.
11. After each major phase, run the project's build/lint checks and fix regressions before continuing.
12. Never overwrite working behavior just to make code look cleaner.

FILE SIZE GUIDELINES

Aim for:
- small focused components
- roughly 100–300 lines where practical
- utility/API modules smaller when possible
- no artificial splitting just to hit a line count

A file can be larger if it represents one coherent responsibility. Do not split code into dozens of meaningless one-function files.

REFACTORING RULE

Prefer this:
Page
  -> hook/state
  -> API module
  -> focused UI components

Instead of:
Page
  -> hundreds of state variables
  -> dozens of fetch calls
  -> CRUD logic
  -> form logic
  -> rendering

The page should primarily orchestrate the feature.
